# 新增一个机器人项目

本仓库是 monorepo：`projects/` 放"某个机器人的完整工程"，`packages/` 放"谁都能用的库"。
这份文档说明**新项目该怎么放**，以及**什么情况下不该放进来**。

## 一、先判断放在哪

| 你想加的东西 | 放哪 | 判断标准 |
| --- | --- | --- |
| 一个机器人的仿真 / 导航 / 抓取工程 | `projects/<project-name>/` | 它是**可独立运行**的完整工程，有自己的环境与构建方式 |
| 多个项目都会用到的算法或工具 | `packages/<package-name>/` | 它**与具体机器人无关**，换一个机器人依然成立 |
| 一个机器人专属、但多个子包共用的工具 | 该项目目录内部 | 只要别的 project 用不上，就不要上升到 `packages/` |
| 与仓库主题无关的东西 | 别处 | 见下文"不该放进来" |

> 铁律：**`projects/` 之间不允许互相依赖。** 需要共用就下沉到 `packages/`。

## 二、目录规范

```
projects/<project-name>/
├── README.md          # 必需：项目入口文档（模板见下）
├── ros2_ws/           # ROS 2 项目：项目自己的工作空间
│   └── src/<pkg>/     #   包名用 snake_case，目录名用 kebab-case
├── docs/              # 可选：项目专属长文档、图片、录屏
├── assets/            # 可选：演示 GIF、架构图（不要放几十 MB 的原始录屏）
└── ...
```

命名：

- 项目目录：`kebab-case`，例如 `ur5-arm-pick`、`mobile-base-nav`
- ROS 2 包：`snake_case`，例如 `ur5_arm_pick`
- Python 包：`snake_case`，并且**目录名必须与 import 名一致**（历史教训：目录叫
  `algorithm_template_model`、包叫 `reusable_model`，直接导致全部测试挂掉）

## 四、接入自检清单

提 PR 前逐条确认：

- [ ] **能在干净环境跑起来**：从 `git clone` 开始，README 里的命令可以复制粘贴一路到底
- [ ] **有验证方法**：明确写出"怎么知道它是好的"，而不是只说"启动成功"
- [ ] **无绝对路径**：不出现 `/home/<某人>/...`；路径一律相对或来自包内 `get_package_share_directory`
- [ ] **无私有资产**：不含公司内部数据、密钥、`.env`、未授权的第三方模型/网格
- [ ] **无构建产物**：没提交 `build/`、`install/`、`log/`、`__pycache__/`
- [ ] **有许可证**：新增第三方资源须说明来源与许可，且与 Apache-2.0 兼容
- [ ] **已通过「五、知识产权自检」**（硬性门槛，不过不接收）
- [ ] **更新了根 `README.md` 与 `projects/README.md` 的说明**
- [ ] **更新了 `CHANGELOG.md`**
- [ ] **公共部分已下沉**：重复代码抽到 `packages/`，而不是复制两份
- [ ] **CI 通过**：`.github/workflows/` 里的检查全绿

## 五、知识产权自检（硬性门槛）

**这一节比其它所有要求都重要。** 本项目曾因为这一条，把一个已经做完、构建验证通过的
完整仿真项目整体移出公开仓库 —— 见 [`NOTICE`](../NOTICE)。

### 绝对不可以提交

| 内容 | 为什么 |
| --- | --- |
| 机器人厂商交付的 URDF / STL / CAD / 网格 | 版权属厂商，随设备交付 ≠ 授权再分发 |
| 从厂商 SDK、厂商网盘、工控机里拷出的任何文件 | 同上，且可能违反保密条款 |
| 从别的二次开发仓库复制的模型或代码 | 你还需要看**那个**仓库的许可 |
| 许可证不明的数据集、模型权重 | 无法判断能否再分发 |
| 公司内部代码、配置、密钥、客户数据 | 保密义务 |

### 关键认知

- **"找不到官方开源仓库" ≠ "可以自由使用"。** 找不到授权 = 默认「保留所有权利」。
- **"别人也传了" ≠ "你也能传"。** 他们同样在被下架的风险中。
- **"这是我自己从模型推导出来的" 仍然是灰色地带。** 由第三方数据推导出的文件
  （例如按包围盒生成的简化几何）也应在 PR 里主动说明。
- **删掉文件 ≠ 从仓库里消失。** 历史 commit 里仍有，必须重写历史
  （`git filter-repo`）才算真正移除。
- ⚠️ **重写历史前必须先 commit。** `git filter-repo` 要求干净工作区，
  它在有未提交改动时可能重置工作区，把没提交的编辑全部冲掉（本项目踩过这个坑）。

### 如果你确实是合作方

合作高校 / 合作企业做二次开发时，请注意：**"二次开发合作" 通常只授权你使用，
不包含再分发**。发布前请确认三件事：

1. 合作协议里的**知识产权归属**与**成果发布 / 保密**条款怎么说
2. 你所在单位（学校 / 公司）的成果对外发布是否需要审批
3. 拿到权利人的**书面许可**，且范围写细：能否再分发？以什么许可证？能否使用商标名称？

### 提交前请回答自己

- [ ] 这个项目里的**每一个**模型 / 网格 / 数据集，我都能说清来源和许可吗？
- [ ] 有没有哪个文件是"从厂商那里拿的"？如果有，删掉它
- [ ] 如果权利人明天来问，我能拿出书面许可吗？
- [ ] 我是否已经把这个项目的历史也一并清理干净（如果之前误传过）？

拿不准就先开 issue 问，**不要先传再说**。

## 六、不该放进来

- 与机器人开发无关的代码、课程作业、临时试验
- 只有一次大提交、无法复现的"代码倾倒"
- 体积巨大的二进制资源（原始点云、录屏、数据集）——请用 Release 附件或外部存储，并在 README 里给出获取方式
- 有许可证冲突的代码：本仓库是 Apache-2.0，GPL 代码不能直接并入
- 任何未通过上文知识产权自检的内容

## 七、这个项目该不该独立成仓库

留在 monorepo 的信号：

- 还在快速演进，接口频繁变动
- 与仓库内其他项目共享概念、术语、约定
- 维护者就是仓库维护者本人

考虑拆出去独立仓库的信号：

- 有独立的外部使用者，需要自己的 issue 追踪与发布节奏
- 需要独立的 CI 时间或平台（例如只能在特定硬件上构建）
- 体积或依赖已经明显拖慢整个仓库的克隆与 CI
- **需要保密**（内部项目不要放在公开 monorepo 里，哪怕用子目录隔离）

即使拆出去，也建议在本仓库 `README.md` 的索引里保留一行链接，形成入口聚合。
