# 多人协作开发规范

> 项目：基于天轶 2.5 的产业合作接待迎宾机器人（代号 `greeting`）
> 关联文档：[酒店迎宾项目规划方案.md](./酒店迎宾项目规划方案.md)、[接口契约冻结表.md](./接口契约冻结表.md)
> 远端仓库：`CGmoke/TianYi-2.5-HIST`（本地 remote 名 `greeting`，SSH：`git@github.com:CGmoke/TianYi-2.5-HIST.git`）
> 文档版本：v1.0　生效日期：2026-10-02　维护人：集成负责人

## 1. 目的与适用范围

本规范约束 **3 人并行开发小组** 在 `greeting` 项目上的日常协作，覆盖：分支模型、分支操作流程、工作空间与命名、接口冻结与变更、提交与评审、待办与风险跟踪。

**不覆盖**：需求定义与验收标准（见规划方案 §2/§10）、现场部署 SOP（见规划方案 §7.8/§12）。

**强制程度**：带 🔴 的条目为硬性红线，违反需在提交记录说明；其余为约定，可在 PR 中讨论修改。

## 2. 角色与包所有权

### 2.1 分工表

| 代号 | 角色 | 负责包 | 核心交付 |
| --- | --- | --- | --- |
| **A** | 迎宾动作（Body/Nav Owner） | `greeting_body`、`greeting_nav` | 礼仪动作库（示教→关键帧→流式下发）、固定范围短距移位 |
| **B** | 语音交互（Voice/Dialog Owner） | `greeting_voice`、`greeting_dialog` | `Speak` Action（TTS 封装 / 打断 / 续播）、受限主题问答,迎宾用语 |
| **C** | 内置视觉感知和语言模型（Vision Owner and LLM model） | `greeting_perception` `greeting_llm_model` | 端侧就位检测（`/greeting/perception/person`）、相机合规开关 |
| **P** | 集成/平台（Platform Owner） | `greeting_interfaces`、`greeting_orchestrator`、`greeting_console`、`greeting_health`、`greeting_bringup`、`greeting_demo` | 唯一状态机、控制台、健康守护、接口契约维护、launch 集成 |

> **P 的归属**：本组仅 3 人，`P` 的职责由 A/B/C 中一人兼任（**待指定**，见 §9.1 待办 T-01），也可由项目负责人直接承担。
> **接口包 `greeting_interfaces`** 虽然归 P 维护，但**任何变更必须 A/B/C 三方会签**（见 §6）。

### 2.2 包所有权规则

1. **一个包只有一个 Owner**，Owner 对该包的目录、话题、参数、测试负责。
2. 非 Owner 修改他人包，🔴 **必须走 PR 并由 Owner 作为评审人**，禁止直接 push 到他人分支。
3. 跨包改动（一次 PR 同时动两个 Owner 的包）必须在 PR 描述中列出双方 Owner 并各请一位 Approve。
4. 空目录/占位包不得提前提交（避免三个人抢建同一个包）。

### 2.3 边界不重叠声明

- **语音链路**：`greeting_voice` 只负责"把文本播出去 / 把声音转成文字"，**不做**内容生成与文案裁决；文案与问答边界由 `greeting_dialog` 负责（同属 B）。
- **视觉**：C 只输出"人是否就位"的辅助信号，🔴 **不驱动接待流程、不做人脸识别、不留存图像**。
- **动作**：A 只接受来自 `greeting_orchestrator` 的 Action goal，🔴 **不接受其他模块直接调用**（单一指挥者原则）。
- 全系统**只有一套状态机**（`greeting_orchestrator`），任何人不得在自己的包里再实现一套流程编排。

## 3. Git 分支规范

### 3.1 分支模型：`main` + `feat/*` + PR（GitHub Flow）

举例：

```
                    ┌── feat/body-motion-salute-bow ──┐
main (受保护)  ──┬───┤                                 ├──► PR ─ squash merge ─► main
                │   └── feat/voice-tts-speak-action ──┘
                └───  feat/vision-presence-detector ──► PR ─► main
```

| 分支 | 用途 | 生命周期 | 保护策略 |
| --- | --- | --- | --- |
| `main` | 唯一集成主干，**随时可编译、可启动** | 长期 | 🔴 受保护：禁直推、禁 force push、必须 PR、必须 CI 通过、至少 1 人 Approve |
| `feat/<role>-<desc>` | 新功能 | ≤ 3 天 | 无 |
| `fix/<role>-<desc>` | 缺陷修复 | ≤ 2 天 | 无 |
| `hotfix/<desc>` | 实机现场救火 | ≤ 1 天 | 事后补 PR，说明原因 |
| `chore` / `docs` / `refactor` / `test` / `ci` + `/<role>-<desc>` | 杂务/文档/重构/测试/流水线 | ≤ 2 天 | 无 |

### 3.2 命名规则

🔴 分支名必须匹配以下正则（小写、短横线分隔、单段 ≤ 40 字符、禁中文/空格/下划线）：

```
^(feat|fix|hotfix|chore|docs|refactor|test|ci)/(body|voice|vision|platform|interfaces|docs)-[a-z0-9]+(-[a-z0-9]+)*$
```

`<role>` 取值表：

| token | 对应 Owner | 示例 |
| --- | --- | --- |
| `body` | A | `feat/body-motion-point-right` |
| `voice` | B | `feat/voice-speak-resume-point` |
| `vision` | C | `feat/vision-presence-detector` |
| `platform` | P | `feat/platform-orchestrator-fsm` |
| `interfaces` | P（三方会签） | `fix/interfaces-health-msg-field` |
| `docs` | 任一 | `docs/readme-quickstart` |

> 建议给成员固定前缀（A 用 `body-`、B 用 `voice-`），一眼可辨归属，冲突时无需沟通。

### 3.3 关于已有的个人分支

远端现存 `moke`、`kingdream-cn` 两条个人分支：

- 🔴 **不作为集成源**，`main` 只接受 PR 合入，禁止从个人分支直接 merge 进 `main`；
- 作为个人实验沙箱（临时脚本、录制数据）；
- 🔴 实验性内容（bag 录制、示教数据、大文件）**不入 Git**（`.gitignore` 已忽略 `*.png/*.jpg/*.npy`等类型文件）；
- 建议在 v1.0 规范落地后由 P 归档或删除这两条分支，避免后来者误用。

### 3.4 分支生命周期

| 阶段 | 要求 |
| --- | --- |
| 创建 | 从**最新 `main`** 拉出，禁止从其他 feat 分支拉出（会造成隐式依赖） |
| 存活 | ≤ 3 天；超过则先拆小或先合入可用的部分 |
| 提交 | 小步提交，单个 commit 只做一件事（见 §8.1） |
| 合并 | **squash merge**（保持 main 线性历史，便于 `git bisect`） |
| 回收 | 合并后立即删除远端与本地分支 |

## 4. 协作分支操作过程（标准动作）

### 4.1 一次性初始化（每人执行一次）

```bash
# 1) 克隆（建议路径：~/work/tianyi25-greeting）
git clone git@github.com:CGmoke/HIST-Robot.git tianyi25-greeting
cd tianyi25-greeting

# 2) 确认远端名与自身身份
git remote -v
git config user.name "你的名字"
git config user.email "你的邮箱"

# 3) 拉取所有分支并确认在 main
git fetch --all --prune
git switch main && git pull --ff-only
git log --oneline -5
```

### 4.2 日常开发循环（每个任务一遍）

```bash
# ① 开新任务前：先同步主干（保证起点最新）
git switch main
git fetch origin --prune            # 若远端名为 greeting 则用 greeting
git pull --ff-only

# ② 拉特性分支（role 按 §3.2 取）
git switch -c feat/voice-tts-speak-action

# ③ 开发 → 编译 → 自测（环境变量见 §5.5）
cd greeting_ws
colcon build --symlink-install && source install/setup.bash
cd ..

# ④ 提交（规范见 §8.1）
git add greeting_ws/src/greeting_voice/          # 按文件/目录精确添加，禁止 git add -A
git commit -m "feat(voice): 新增 Speak Action 服务端骨架与取消逻辑"

# ⑤ 推送并建立跟踪
git push -u origin feat/voice-tts-speak-action
```

### 4.3 发起 PR

```bash
# 用 gh 创建（推荐，便于统一模板）
gh pr create \
  --base main \
  --head feat/voice-tts-speak-action \
  --title "feat(voice): Speak Action 服务端与 TTS 封装" \
  --body "$(cat <<'EOF'
## 变更内容
- 实现 greeting_voice/speak_server.py（Speak Action 服务端）
- 封装 /intelligent_interaction/tts/play（cmd:'append'），长文本分段
- 支持 cancel goal 打断 + resume_point 续播

## 涉及接口
- 新增 Action 服务端：/greeting/speak（契约见《接口契约冻结表.md》§4.3）
- 是否修改 greeting_interfaces：否

## 验证方式
- [ ] colcon build 通过
- [ ] colcon test 通过
- [ ] ros2 action send_goal /greeting/speak ... 实测打断与续播
- [ ] 干跑模式（不驱动本体）日志符合预期

## 风险 / 未完成
- ASR 未接入，问答环节由主持人代答兜底
EOF
)"
```

### 4.4 评审与合并

```bash
# 评审人本地验证（🔴 必须真实编译过，不能只读 diff）
gh pr checkout 42
cd greeting_ws && colcon build --symlink-install && colcon test && cd ..
# 通过后 approve
gh pr review 42 --approve --body "本地编译 + 实测通过"
```

合并方式（由 PR 作者或 P 执行）：

```bash
gh pr merge 42 --squash --delete-branch
git switch main && git pull --ff-only
```

### 4.5 同步主干（特性分支未合并期间）

```bash
git switch feat/voice-tts-speak-action
git fetch origin --prune
git rebase origin/main          # 🔴 用 rebase，不用 merge，保持线性
# 若 rebase 产生冲突 → 见 §4.6
git push --force-with-lease     # 🔴 只能对自己的 feat 分支用 --force-with-lease
```

### 4.6 冲突处理

```bash
git rebase origin/main
git status                      # 查看冲突文件
# 手工解决冲突（🔴 不允许整文件 -X theirs/ours 糊过去）
git add <已解决的文件>
git rebase --continue
# 中途放弃
git rebase --abort
```

**冲突高发区**（提前沟通，减少冲突）：

| 文件 | 冲突原因 | 规避 |
| --- | --- | --- |
| `greeting_interfaces/**` | 三方都加字段 | 🔴 变更前先在 Issue 中登记（§6.3），由 P 统一改 |
| `greeting_bringup/config/*.yaml` | 各自加参数 | 按包分文件（`body.yaml`/`voice.yaml`/`perception.yaml`），P 负责合并 launch |
| `greeting_bringup/launch/greeting.launch.py` | 都往里加节点 | 🔴 只允许 P 修改，其他人在 PR 中提要求 |
| `README` / 文档 | 都改 | 按章节分工，避免整段重写 |

### 4.7 实机现场救火（hotfix）

```bash
git switch main && git pull --ff-only
git switch -c hotfix/tts-play-null-text-crash
# 最小改动 + 现场验证
git commit -m "fix(voice): 修复空文本调用 TTS 导致服务挂死"
git push -u origin hotfix/tts-play-null-text-crash
gh pr create --base main --title "hotfix(voice): ..."   # 🔴 走 PR，不直推 main
gh pr merge <PR号> --squash --delete-branch
```

现场无网时：可先本地验证并**记录补丁内容**，回到有网环境立即补 PR（Issue 中标注 `hotfix-pending`）。

### 4.8 联调集成标签

每次多人实机联调前，P 打一个集成标签，便于回溯"当时大家跑的是哪一版"：

```bash
git switch main && git pull --ff-only
git tag -a integration/20261015 -m "首次三人实机联调（动作+语音+视觉）"
git push origin integration/20261015
```

### 4.9 常见故障速查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `Failed to connect to github.com port 443` | 全局 http/https 代理已配置但代理未启动 | `git config --global --unset http.proxy`（或先启动本地代理） |
| `push` 被拒：`protected branch` | 试图直推 `main` | 改为推 feat 分支 + PR |
| `push` 被拒：`non-fast-forward` | 远端 feat 分支已被 rebase 过 | 用 `git push --force-with-lease`（仅限自己的 feat 分支） |
| 切分支后 `ros2 run` 找不到包 | `build/install` 未随分支更新 | 重新 `colcon build`（见 §5.6） |

### 4.10 🔴 禁止事项清单

1. 直推 `main`、对 `main` 执行 force push；
2. 对他人分支执行 `push --force`；
3. `git add -A` / `git add .`（避免误提交大文件、录制数据、密钥）；
4. 提交 `build/`、`install/`、`log/`、`.bag`、示教原始数据、`.npy`、图像文件；
5. 提交任何密钥、IP 白名单之外的凭据、客户未审核文案；
6. 在同一个 PR 中同时修改接口契约与业务逻辑（🔴 接口变更必须独立 PR，见 §6.3）；
7. 长期不合并的"僵尸分支"（> 3 天）。

## 5. 工作空间与命名规范

### 5.1 工作空间

| 项 | 规定 | 理由 |
| --- | --- | --- |
| 工作空间名 | 🔴 固定为 `greeting_ws` | 与规划方案 §6 一致；launch/脚本中的相对路径可跨机器复用 |
| 位置 | 仓库根目录下的 `greeting_ws/`（`<repo>/greeting_ws`） | 每人克隆路径可不同，但**仓库内相对路径必须一致** |
| 源码目录 | 只允许 `<repo>/greeting_ws/src/` | 🔴 禁止在 `src/` 下嵌套第二个工作空间 |
| 构建目录 | `build/` `install/` `log/` **不入库** | `.gitignore` 已覆盖 |
| 个人实验 | 复制到 `~/work/exp_<name>_ws` 后自由改，🔴 不回灌仓库 | 避免污染主干 |

🔴 禁止：中文路径、空格路径、把仓库放到网络盘/同步盘（会破坏 `colcon` 的符号链接与权限）。

### 5.2 包命名

| 规则 | 说明 |
| --- | --- |
| 🔴 全小写下划线 | `greeting_body`，禁止 `GreetingBody`、`greeting-body` |
| 统一前缀 | 自建包一律 `greeting_`；接口包固定 `greeting_interfaces` |
| 一个包一件事 | 不建 `greeting_utils` 这类"什么都装"的包；通用工具放各自包内 |

### 5.3 节点 / 话题 / 服务 / Action / 参数命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 节点名 | 小写下划线，`snake_case`，与文件名一致 | `motion_server`、`presence_detector_node` |
| 自建话题 | 一律 `/greeting/` 前缀 + 小写下划线 | `/greeting/control_cmd`、`/greeting/perception/person` |
| 服务 | `/greeting/` 前缀，动词或名词短语 | `/greeting/control`、`/greeting/reload_script` |
| Action | `/greeting/` 前缀，动词短语 | `/greeting/speak`、`/greeting/navigate_to`、`/greeting/play_motion` |
| 🔴 本体/底盘接口 | **原样使用，禁止重命名、禁止再包一层同名话题** | `/head/cmd`、`/arm/cmd`、`/waist/cmd`、`/diagnose/robot_state` |
| 参数名 | 小写下划线，在 YAML 中声明 | `speed_scale`、`waypoint`、`timeout_s` |
| 消息字段 | 小写下划线，符合 ROS2 风格 | `distance_m`、`bearing_rad`、`operator_id` |
| 单位后缀 | 🔴 数值字段必须带单位后缀 | `_m` 米、`_rad` 弧度、`_s` 秒、`_pct` 百分比 |

### 5.4 目录与文件命名

```
greeting_ws/src/greeting_body/
					├── greeting_body/                 # Python 模块目录（与包同名）
					│   ├── motion_server.py           # Action 服务端
					│   ├── body_adapter.py            # /head/cmd /arm/cmd /waist/cmd 封装 + 预检
					│   └── motions/                   # 关键帧数据
					│       ├── salute_bow.json
					│       └── wave_official.json
					├── config/
					│   └── motions.yaml
					├── launch/
					├── test/
					├── resource/greeting_body         # ament 资源标记（Python 包必填）
					├── package.xml
					└── setup.py / setup.cfg
```

- 🔴 关键帧 JSON 文件用**动作名**命名（`salute_bow.json`），与 `PlayMotion.action` 中 `motion_name` 严格一致（禁止拼音、禁止别名）。
- 讲稿/文案文件：`script.yaml` 需带版本号字段（`script_version`），与审核记录对应（规划方案 §7.7 L5）。
- 配置按 Owner 拆文件：`body.yaml`、`voice.yaml`、`perception.yaml`、`platform.yaml`，🔴 避免三人挤同一个 YAML。

### 5.5 环境基线（每个终端、每次操作前必做）

**通用前置**（实机必做，必须在启动任何节点之前执行）：

```bash
export ROS_LOG_DIR=/tmp/ros_log ROS_HOME=/tmp/ros_home PYTHONDONTWRITEBYTECODE=1
```

**实机（天轶 2.5 工控机 / Jetson AGX Thor）** —— 🟢 顺序不可交换：

```bash
source /opt/ros/jazzy/setup.bash                  # 1. ROS2 底座
source $HOME/xos/setup.bash                       # 2. 厂商 SDK：提供 ros2_bridge_msgs
source <repo>/greeting_ws/install/setup.bash      # 3. 本项目工作区：必须最后 source
```

> 🔴 `ROS_LOG_DIR` 必须先于启动节点设置，否则 `robot_state_publisher` 会因日志目录权限拒绝启动。
> 🔴 严禁把 `xarm_sim_stack_full/setup.bash` 加入任何启动脚本，严禁其 `lib` 混入 `LD_LIBRARY_PATH`（aarch64 二进制，会导致本机不可执行）。
> 🟢 `$HOME/xos/setup.bash` 是**机器本地**文件（不随仓库分发），提供实机通道 `/head/cmd`、`/arm/cmd`、`/waist/cmd`、`/robot_state` 所需的 `ros2_bridge_msgs`；其内部已自带 `source /opt/ros/jazzy/local_setup.bash`，但仍要求显式先 source 第 1 步，便于排错时确认底座版本。
>
> **环境自检**（实机开跑前执行一次）：

```bash
ros2 pkg prefix ros2_bridge_msgs # 必须输出 $HOME/xos/...（缺失说明第 2 步没做）
```

### 5.6 切换分支后的构建要求

由于 `build/` `install/` 不入库且**不随分支切换**：

```bash
git switch <另一分支>
cd greeting_ws
rm -rf build install log        # 🔴 接口包变更后必须全量重建
colcon build --symlink-install
source install/setup.bash
```

**接口包（`greeting_interfaces`）的任何变更后，必须全量重建**，否则会出现"消息类型找不到 / 字段缺列"的假故障。

## 6. 接口冻结与变更流程

### 6.1 冻结范围

冻结对象为 **`greeting_interfaces` 包的全部 msg / srv / action 定义**，以及**话题/服务/Action 的名称与 QoS**，清单见 [接口契约冻结表.md](./接口契约冻结表.md)。

| 层级 | 内容 | 冻结状态 |
| --- | --- | --- |
| L1 消息定义 | `.msg` / `.srv` / `.action` 字段与顺序 | 🔴 已冻结（变更走 §6.3） |
| L2 接口名 | 话题/服务/Action 的字符串名 | 🔴 已冻结 |
| L3 QoS | 可靠性、历史深度、持久性 | 🔴 已冻结（不匹配会导致"话题在但收不到数据"） |
| L4 语义 | 字段单位、取值范围、枚举含义 | 🔴 已冻结（写进契约表） |
| L5 实现 | 各包内部如何实现 | 🟢 不冻结，Owner 自主 |

### 6.2 冻结期规则（三人并行期间）

1. 🔴 **先冻结、后开发**：任何人在写业务代码前，若需要新接口，先在 Issue 中提案（§6.3），通过后再动代码。
2. 🔴 **禁止"我本地先改 .msg 试试"**：本地改了接口会导致其他人的包编译失败，属最高优先级事故。
3. 需要临时结构时，🔴 用**包内私有消息**或 `std_msgs`，禁止提交到 `greeting_interfaces`。
4. 契约表是唯一事实来源；代码与契约表不一致时，🔴 **以契约表为准**，先改代码。

### 6.3 接口变更流程（4 步）

```bash
# ① 提案：在 GitHub Issue 登记（标题前缀 [INTERFACE]），说明
#    - 变更内容：加字段 / 改类型 / 改 QoS / 新增接口
#    - 影响范围：谁会受影响（@A @B @C）
#    - 兼容性：是否破坏性（破坏性变更必须写迁移方案）
#    - 目标日期

# ② 会签：A/B/C 三方在 Issue 中确认（至少"无异议"），P 记录结论
#    🔴 破坏性变更需三方明确 Approve，不能默认通过

# ③ 实施：P 单独开接口 PR（🔴 不得混入业务代码）
git switch main && git pull --ff-only
git switch -c fix/interfaces-health-msg-field
# 只改 greeting_interfaces/**
git commit -m "fix(interfaces): SubsystemHealth 新增 audio_detail 字段"
git push -u origin fix/interfaces-health-msg-field
gh pr create --base main --title "fix(interfaces): ..."   # 需 A/B/C 至少 2 人 Approve

# ④ 广播 + 同步：合并后在 Issue 中 @所有人，并在群里发一条变更公告
#    各人立即执行：
git switch main && git pull --ff-only
cd greeting_ws && rm -rf build install log && colcon build --symlink-install
```

**变更分级与响应时限**：

| 级别 | 定义 | 审批 | 响应时限 |
| --- | --- | --- | --- |
| P0 破坏性 | 改字段类型/删除字段/改接口名/QoS | 三方 Approve | 立即，暂停相关开发 |
| P1 增量 | 新增可选字段/新增接口 | 1 人 Approve + 三方知会 | 24h 内同步 |
| P2 文档级 | 注释、单位说明、枚举注释 | Owner 自审 | 随下一个 PR |

### 6.4 版本号与兼容性

- `greeting_interfaces` 的 `package.xml` 版本号按 `主.次.修订` 管理：**P0 → 主 +1，P1 → 次 +1，P2 → 修订 +1**。
- 🔴 字段只增不删、不改类型；确需删除时，先标记 `# DEPRECATED since vX.Y` 保留一个大版本。
- 字段追加时 🔴 **必须加在末尾**，禁止插在中间（会破坏已编译的旧包）。
- 每次变更在契约表 §9 变更记录中追加一行（日期 / 版本 / 内容 / 提出人 / 会签人）。

### 6.5 Mock 与临时接口约定

三人并行时必然出现"对方还没实现"的情况，统一约定：

| 场景 | 做法 |
| --- | --- |
| 依赖的 Action 服务端未就绪 | 用 `greeting_demo/` 下的 mock 服务端（🔴 只能放 `greeting_demo`，不许进业务包） |
| 依赖的本体硬件不可达 | 各包内提供 `--dry-run` / `simulate` 参数，走日志不驱动硬件 |
| 需要占位数据 | 🔴 用真实字段名 + 合理量纲的假值（如 `distance_m: 2.5`），禁止 `-1` / `NaN` 等无意义值 |
| Mock 的清理 | 对应真实实现合入后，🔴 在同一个 PR 中删除 mock，避免长期残留 |

## 7. 各模块接口速查

> 完整定义（字段、单位、QoS）见 [接口契约冻结表.md](./接口契约冻结表.md)。此处只列"谁碰哪些接口"，用于快速判断改动会影响谁。

### 7.1 成员 A — 迎宾动作（`greeting_body` / `greeting_nav`）

| 接口 | 类型 | A 的角色 |
| --- | --- | --- |
| `/greeting/play_motion` | Action `PlayMotion` | 🔴 服务端（唯一实现） |
| `/greeting/navigate_to` | Action `NavigateTo` | 🔴 服务端（唯一实现） |
| `/head/cmd` `/arm/cmd` `/waist/cmd` | Topic `ros2_bridge_msgs/*` | 发布（10Hz 流式，`--times 20` 保持） |
| `/diagnose/robot_state` | Topic（类型待确认） | 订阅（动作预检、安全姿位确认） |
| 底盘 REST `:9090`（`moveto` / `moveby` / `GET actions/{id}`） | HTTP | 调用方 |
| `/greeting/health` | Topic `SubsystemHealth` | 订阅（通道不可用时降级为"仅语音"） |

🔴 A 的硬约束：动作下发前必须 `ros2 topic info /arm/cmd` 确认 `Subscription count ≥ 1`；单次位置差 ≤ 1.9 rad；`speed_scale ≤ 0.7`；腿部关节禁止使用。

### 7.2 成员 B — 语音交互（`greeting_voice` / `greeting_dialog`）

| 接口 | 类型 | B 的角色 |
| --- | --- | --- |
| `/greeting/speak` | Action `Speak` | 🔴 服务端（唯一实现） |
| `/greeting/intent` | Topic `GreetingIntent` | 🔴 发布方（问答环节） |
| `/intelligent_interaction/tts/play` | Service `interaction_msgs/srv/TtsService` | 调用方（`cmd:'append'`） |
| `/intelligent_interaction/interactive/state` | Service `InstructionService` | 调用方（仅问答环节启停） |
| `/greeting/health` | Topic `SubsystemHealth` | 订阅（音频异常时告警） |

🔴 B 的硬约束：TTS **无 stop 接口**，打断只能靠 Action `cancel goal` 实现；长文本必须分段；音频链路异常不得阻塞主流程。

### 7.3 成员 C — 视觉感知（`greeting_perception`）

| 接口 | 类型 | C 的角色 |
| --- | --- | --- |
| `/greeting/perception/person` | Topic `PersonDetection` | 🔴 发布方（唯一） |
| `/greeting/events` | Topic `GreetingEvent` | 发布方（`EVENT_LEADER_ARRIVED` 等，`source: perception`） |
| `/ob_camera_head/color/image_raw` | Topic `sensor_msgs/Image` | 订阅（30Hz，`best_effort`） |
| `/ob_camera_head/depth/image_raw` | Topic `sensor_msgs/Image` | 订阅（可选） |
| `/ob_camera_head/set_streams_enable` | Service `std_srvs/srv/SetBool` | 调用方（合规开关） |

🔴 C 的硬约束：输出**只是提示**，不得触发接待流程；🔴 严禁人脸识别、严禁图像留存；相机流必须支持一键关闭。

### 7.4 成员 P — 平台/编排（共享）

| 接口 | 类型 | P 的角色 |
| --- | --- | --- |
| `/greeting/control_cmd` | Topic `ConsoleCommand` | 订阅（编排层入口） |
| `/greeting/panel_command` | Topic `String` | 订阅（按键兜底） |
| `/greeting/control` `/greeting/reload_script` | Service `GreetingControl` | 服务端 |
| `/greeting/state` | Topic `String`（`transient_local`） | 发布（控制台显示） |
| `/greeting/health` | Topic `SubsystemHealth` | 🔴 发布方（唯一） |
| `/greeting/speak` `/greeting/navigate_to` `/greeting/play_motion` | Action | 🔴 客户端（唯一调用者） |

🔴 P 的硬约束：只有 P 能修改 `greeting_bringup/launch/*.py`；编排层是唯一指挥者，其他模块之间禁止互相调用。

## 8. 提交规范与代码评审

### 8.1 提交信息规范（Conventional Commits）

格式：

```
<type>(<scope>): <中文简述，≤ 50 字>

[可选] 变更原因与影响
[可选] Refs #123 / BREAKING CHANGE: ...
```

**type 取值**：`feat` 新功能 / `fix` 缺陷 / `docs` 文档 / `style` 格式 / `refactor` 重构 / `perf` 性能 / `test` 测试 / `build` 构建 / `ci` 流水线 / `chore` 杂务 / `revert` 回退。

**scope 取值**（🔴 必须与包或职责对应）：

| scope | 对应 |
| --- | --- |
| `interfaces` | `greeting_interfaces` |
| `orchestrator` / `console` / `health` / `bringup` / `demo` | P 的包 |
| `body` / `nav` | A 的包 |
| `voice` / `dialog` | B 的包 |
| `perception``llmmodel` | C 的包 |
| `docs` / `ci` | 文档与流水线 |

示例：

```
feat(body): 新增 salute_bow 鞠躬关键帧与分段插值
fix(voice): 修复空文本调用 TTS 导致服务挂死
docs(interfaces): 补充 SubsystemHealth 各字段单位说明
fix(interfaces)!: 移除 PersonDetection.confidence 字段

BREAKING CHANGE: confidence 由检测端下移到编排层计算，@C @P 需同步
```

🔴 一个 commit 只做一件事；🔴 禁止 `update`、`fix bug`、`111` 之类无信息量的提交信息。

### 8.2 PR 规则

| 项 | 要求 |
| --- | --- |
| 标题 | 与 commit 规范同格式 |
| 体积 | 建议 ≤ 400 行 diff；超出请拆分 |
| 描述 | 必须包含：变更内容 / 涉及接口 / 验证方式 / 风险与未完成（见 §4.3 模板） |
| 关联 | 必须关联 Issue（`Refs #N` 或 `Closes #N`） |
| 前置 | 🔴 作者必须本地 `colcon build` + `colcon test` 通过 |
| 接口变更 | 🔴 涉及 `greeting_interfaces` 的 PR 必须附 Issue 链接与三方会签结论 |

### 8.3 评审规则

| 场景 | 评审人 | Approve 数 |
| --- | --- | --- |
| 单包业务改动 | 该包 Owner（若非本人）/ 任一成员 | 1 |
| 跨包改动 | 双方 Owner | 各 1 |
| `greeting_interfaces` | A + B + C 中至少 2 人 | 2 |
| `greeting_bringup/launch` | P | 1 |
| hotfix | 任一成员事后评审 | 1（可事后补） |

**评审检查项（Reviewer 必查）**：

- [ ] 分支名 / commit 信息符合 §3.2、§8.1；
- [ ] 🔴 未修改 `greeting_interfaces`（除非本 PR 就是接口 PR）；
- [ ] 🔴 未提交 build/install/log、bag、图像、大文件、密钥（`git diff --stat` 核对）；
- [ ] 命名符合 §5.3（话题前缀、单位后缀、`snake_case`）；
- [ ] QoS 显式声明且与契约表一致（自建话题订阅端尤其注意）；
- [ ] 🔴 动作类接口有安全姿位收尾 / 超时 / 取消处理；
- [ ] 日志使用 ROS 标准接口（`rclpy` 的 `get_logger()`），无裸 `print`；
- [ ] 已本地构建并实测，作者提供了验证命令与预期输出。

评审时限：🟠 收到 review request 后 **24h 内**给出意见（可先给"待细看"占位）。

### 8.4 合并前后检查

**合并前**：CI 绿 / Approve 达标 / 无未解决讨论 / 已 rebase 到最新 `main`。
**合并后**：作者删除分支；🔴 **P 在 24h 内验证 `main` 可完整构建并跑通最小链路**（`greeting_demo` smoke test）；若接口变更，P 发广播。

## 9. 待办与风险跟踪

### 9.1 看板与标签

使用仓库所在的 GitHub Issues + Projects 看板（无额外工具成本）：

**列**：`Backlog` → `Todo` → `In Progress` → `Review` → `Done`（🔴 每人同一时刻 `In Progress` ≤ 2 项）

**标签**：

| 类别 | 标签 |
| --- | --- |
| 归属 | `area:body` `area:voice` `area:vision` `area:platform` `area:interfaces` |
| 类型 | `type:feature` `type:bug` `type:task` `type:risk` `type:docs` |
| 优先级 | `P0` `P1` `P2` |
| 状态 | `blocked` `needs-decision` `hotfix-pending` `interface-change` |

**Issue 必填字段**：标题、归属 `area`、验收标准（可验证）、依赖项。

### 9.2 待办与风险跟踪模板

```markdown

（为什么做这件事）

- [ ] 可验证的条件 2

- 需要 @某人 提供 …

## 风险
（若延期或失败会怎样；应对方案）
```

### 9.3 同步节奏

| 节奏 | 形式 | 内容 |
| --- | --- | --- |
| 每日 | 看板更新 | 昨晚完成 / 今天计划 / 有无阻塞（🔴 不刷屏，只动看板） |
